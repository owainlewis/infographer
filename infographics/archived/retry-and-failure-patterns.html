How to Build Reliable Software

01
Timeout

The first line of defense. Every outbound call needs a deadline. Without one, a hung dependency holds your threads hostage until the process runs out of resources. Set aggressive timeouts and let callers retry — a fast failure is better than a slow one. Use separate connect and read timeouts.

First defense Connect + Read Fail fast
02
Exponential Backoff

Don't hammer a failing service. Wait 1s, 2s, 4s, 8s between retries. Add jitter so all clients don't retry at the same instant. Cap the maximum delay. Without jitter, a thundering herd retries in sync and takes down the recovering service all over again. Most SDKs have this built in.

Jitter required 1s → 2s → 4s → 8s Cap max delay
03
Circuit Breaker

Stop calling a service you know is down. Track failure rate. When it crosses a threshold, trip the circuit — all calls fail immediately without hitting the downstream. After a cooldown, let one request through (half-open). If it succeeds, close the circuit. If not, back to open. Three states: closed → open → half-open.

Resilience4j Three states Fail without waiting
04
Bulkhead

Isolate failures so they can't spread. Name comes from ship compartments — flood one, the ship stays afloat. Give each dependency its own thread pool or connection pool. If the payment service is slow, it exhausts its pool but the search service keeps running. Without bulkheads, one slow dependency drains all your resources.

Resource isolation Thread pools Blast radius
05
Fallback

Degrade gracefully instead of failing completely. When the primary path fails, return cached data, a default response, or a simplified result. Show yesterday's recommendations instead of none. Return a generic error page instead of a stack trace. The user experience degrades but doesn't break. Design fallbacks before you need them.
