Caching Strategies

The Big Picture
How Caching Works

Every strategy answers two questions: where do reads come from, and when do writes reach the database? The hard part is never caching. It's invalidation.

Redis Memcached Invalidation is the hard part
01 · Read
Cache-Aside

The one you'll use 90% of the time. App checks cache, misses go to DB, result gets stored. Under load, a cold key can trigger a stampede: hundreds of concurrent misses all hitting the DB at once.

Redis Stampede risk
02 · Read
Read-Through

Same as cache-aside, but the cache fetches on miss. The difference is who loads: your app code (cache-aside) vs the cache layer itself (read-through). The DB still gets hit on every miss.

Ehcache Caffeine
03 · Predictive
Refresh-Ahead

Reload before anyone notices it's stale. When a key nears expiry, the cache pre-fetches from DB. If your predictions are wrong, you waste DB reads refreshing keys nobody asks for.

Hot keys only Prediction risk
04 · Write
Write-Through

Cache and DB updated in the same call. The write blocks until both cache and DB confirm. No stale reads, but every write pays the latency of two sequential stores.

Strong consistency Blocking
05 · Write
Write-Behind

Write to cache, ACK instantly. Cache flushes to DB async. If the cache node dies before flushing, those writes are permanently lost. Not an option for financial data or anything you can't afford to lose.

Throughput Durability risk
06 · Write
Write-Around

Skip the cache on writes. Data goes straight to DB. Cache only fills when someone actually reads it. Prevents polluting your cache with data nobody queries.
