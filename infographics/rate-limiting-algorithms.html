Rate Limiting Algorithms

01
Fixed Window

The simplest counter you can build. Count requests per fixed time window (e.g., 100/minute). Counter resets at each boundary. Problem: a burst at 0:59 and another at 1:01 doubles your intended rate in a 2-second span.

Tradeoff — Simple to implement, but boundary bursts can double throughput.

Redis INCR Simplest Boundary burst risk
02
Sliding Window Log

Fixes the boundary problem by tracking every timestamp. Keep a sorted log of request timestamps. Count entries within the last N seconds. Perfectly accurate, but storing every timestamp gets expensive at high throughput.

Tradeoff — Precise rate limiting, but O(n) memory per user.

Precise Memory-heavy Sorted set
03
Token Bucket

The algorithm behind AWS and Stripe rate limits. Bucket holds N tokens, refills at a steady rate. Each request takes a token. Bucket empty? Request denied. Allows controlled bursts up to bucket capacity, then smooths to the refill rate.

Tradeoff — Allows bursts (good for real traffic), tunable via bucket size and refill rate.

AWS / Stripe Burst-friendly Most popular
04
Leaky Bucket

Smooths everything to a constant output rate. Requests enter the bucket at any speed. The bucket drains at a fixed rate. If it overflows, excess requests are dropped. No bursts ever reach your backend — guaranteed constant throughput.

Tradeoff — Perfectly smooth output, but legitimate bursts get queued or dropped.

NGINX Constant rate No bursts
