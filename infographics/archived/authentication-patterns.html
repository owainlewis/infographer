Authentication Patterns

01 Stateful
Session Tokens

Server creates a session ID, stores state server-side, sends an opaque token in a cookie. Every request looks up state in a DB or cache. Simple to revoke — delete the row.

Best for: Server-rendered apps, admin panels, anything where instant revocation matters.

Server-side state Cookie-based Instant revoke
02 Stateless
JWT

Self-contained signed token with claims inside. Server never stores anything — just verifies the signature. Fast to validate but impossible to revoke until it expires. Keep expiry short.

Best for: Microservices, API auth between services, anywhere you can't afford a DB lookup per request.

Stateless Self-contained Short-lived
03 Delegated
OAuth 2.0

Authorization framework, not authentication. User grants limited access to a third party without sharing credentials. The token represents what you can do, not who you are. Add OIDC for identity.

Best for: Third-party integrations, "Sign in with Google", granting scoped API access.

Delegated Scoped access OIDC for identity
04 Simple
API Keys

A long random string sent in a header. No user context, no expiry logic built in. Easy to issue, easy to leak. Identifies the calling application, not the user. Rate limit and rotate frequently.

Best for: Server-to-server calls, public APIs with usage billing, webhook verification.

App-level identity Simple Rotate often
05 Infrastructure
mTLS

Both client and server present certificates. The TLS handshake itself is the auth layer — no tokens, no passwords. Strong identity guarantee but complex certificate management. Used where trust must be absolute.

Best for: Service mesh auth, zero-trust networks, financial/healthcare inter-service communication.

Mutual certificates Zero-trust Infrastructure-level
